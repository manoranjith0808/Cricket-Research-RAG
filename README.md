# Cricket Research Answer Bot — RAG Capstone

A Retrieval-Augmented Generation (RAG) chatbot that answers questions over a
curated set of cricket research papers, built as a GenAI capstone project.
This README explains not just *how to run it*, but *why every piece is
built the way it is* — treat it as a study guide alongside the code.

---

## 1. What this project does

```
PDFs  →  load & chunk  →  embed (2 models)  →  ChromaDB  →  retrieve (2 strategies)  →  LLM  →  grounded answer + citations
```

Ask a question about the indexed cricket papers, and the system:
1. Retrieves the most relevant passages from the papers
2. Feeds them to an LLM along with strict grounding instructions
3. Returns an answer **plus the top-3 source passages** (paper title + page number) it was based on

```
│   ├── data_loading.py              <- Step 1: PDF -> Documents

│   ├── vectorstore.py               <- Step 4: ChromaDB indexing
│   ├── retrieval.py                 <- Step 5: dense + hybrid retrieval

│

```

**Why split into `src/` modules instead of one big notebook?** The notebook
and `app.py` both need the exact same logic. Writing it once in `src/` and
importing it from both means the notebook you demo and the app you demo are
*provably* running the same pipeline — nothing can drift out of sync between
them, and it's also just easier to read one function at a time than one
giant notebook cell.

## 3. Setup

```bash
cd Cricket-Research-Answer-Bot
pip install -r requirements.txt

cp .env.example .env
# then edit .env and paste your real GEMINI_API_KEY
```

The open-source embedding model (`BAAI/bge-m3`) needs no key but downloads
~2GB of weights the first time it runs. The LLM backend is powered by Google
Gemini, supporting toggling between `3.1-flash-lite`, `3.1-flash`, and
`3.1-pro`. Set `GEMINI_API_KEY` in `.env`.

**Sample data is already included.** Three short PDFs (cricket analytics,
fast-bowling biomechanics, T20 powerplay/death-overs strategy) live in
`data/papers/` — generated by `data/generate_sample_papers.py` so you can
run the whole pipeline with zero setup. To use your own papers (e.g. real
sports-science or cricket-analytics papers), just drop PDFs into
`data/papers/` — nothing else changes.

## 4. Running it

**Notebook (main deliverable):**
```bash
jupyter notebook notebooks/Cricket_Research_Answer_Bot.ipynb
```
Run cells top to bottom. Steps 1–2 need no API keys; Step 3 onward needs
`GEMINI_API_KEY` set.

```bash
streamlit run app.py
```

**Offline plumbing check** (proves indexing/retrieval logic works without
any API key — useful if you just want to sanity-check the code first):
```bash
python3 tests_offline_smoke.py
```

## 5. The pipeline, explained step by step

### Step 1 — Data Loading (`src/data_loading.py`)
Uses `PyPDFLoader` because it returns one `Document` per **page** with the
page number already attached to its metadata. That's the exact granularity
needed later to cite "paper title, page N." `PDFPlumberLoader` is a good
alternative if your PDFs have tables you need to preserve — plain text
extraction can mangle table structure.

### Step 2 — Chunking (`src/chunking.py`)
`RecursiveCharacterTextSplitter`, 700 characters per chunk, 120 character
overlap. It tries splitting on paragraph breaks first, then lines, then
sentences — only falling back to a hard character cut as a last resort, so
chunks stay coherent instead of being sliced mid-sentence.

- **Chunk too small** → loses surrounding context; the LLM may misread an
  isolated sentence.
- **Chunk too large** → mixes multiple ideas into one embedding, diluting
  it and hurting retrieval precision.
- **Overlap** prevents losing a sentence that happens to fall exactly on a
  chunk boundary.

Metadata (`paper_title`, `page_number`, `source_file`) is automatically
inherited by every chunk from its parent page — this is what makes citation
possible downstream; don't strip metadata before this step.

### Step 3 — Embeddings (`src/embeddings.py`)
Two models, compared as required by the brief:

| Model | Type | Notes |
|---|---|---|
| `BAAI/bge-m3` | Open-source, local | Free, no API key, needs local compute |
| `models/text-embedding-004` | Commercial, Gemini API | Fast, small per-token cost |

Both are wrapped behind the same interface so the rest of the pipeline
doesn't care which is active — you can swap between them by passing a
different embedding object into `build_vectorstore()`.

### Step 4 — Vector Database (`src/vectorstore.py`)
**ChromaDB**, chosen over FAISS because it stores metadata (paper title,
page number) alongside each vector natively — a similarity search returns
ready-to-cite results directly. FAISS only stores raw vectors, so you'd need
a separate parallel structure mapping vector index → metadata yourself. We
build **one Chroma collection per embedding model** so the two can be
compared without overwriting each other.

### Step 5 — Retrieval Strategies (`src/retrieval.py`)
1. **Dense retrieval (cosine similarity)** — the baseline. Fast, works well
   when the query's wording resembles the source text.
2. **Hybrid retrieval (BM25 + dense)** — combines a keyword-based score
   (BM25, which rewards exact term overlap) with the dense similarity score
   via rank fusion. This catches specific technical terms (e.g. "powerplay",
   "acute:chronic workload ratio") that pure semantic search can sometimes
   rank lower, while still keeping dense retrieval's ability to match
   differently-worded queries.

### Step 6 — RAG Chain (`src/rag_chain.py`) — "the brain"
This is where retrieval and generation are wired together via LangChain's
LCEL (`|` pipe syntax):

```
retriever → format chunks into labeled context → prompt → gemini-2.5-flash → answer
```

Key prompt engineering decisions:
- The system prompt instructs the model to answer **only** from the
  retrieved context, never from its own trained knowledge.
- It's told to say **"I don't know"** when the context is insufficient
  rather than guess — the single biggest lever against hallucination.
- Every chunk is labeled with its paper title + page number *inside* the
  prompt itself, so the model can naturally reference sources.
- `temperature=0.0` keeps answers deterministic — important for a factual
  QA system, unlike creative writing tasks where you'd want higher
  temperature.

The `ask()` function caps retrieved chunks to the same top-K count both for
what's fed to the LLM *and* what's displayed as sources — this keeps the
answer and its citations always consistent, even though the hybrid
retriever can internally return more candidates before ranking.

### Step 7 — Testing & Evaluation (in the notebook)
10 test questions spanning all 3 papers, including one deliberately
out-of-scope question ("What is the capital of France?") to verify the
system correctly refuses rather than hallucinating an answer. An optional
RAGAS-based automated scoring script is in `evaluation/run_ragas_eval.py`.

### Step 8 — Stretch Goal: Streamlit UI (`app.py`)
Implements Advanced Option 2 from the brief. Reuses every `src/` module —
no logic duplicated between notebook and app. Includes a sidebar toggle to
switch between dense and hybrid retrieval live, which is a good thing to
demo during your viva to show you understand the difference concretely.

## 6. A note on library versions

LangChain released a major version 1.x that restructured around agentic
workflows and moved/renamed several retriever classes used here
(`EnsembleRetriever`, `BM25Retriever`). This project pins to the **stable
0.3.x line** (see `requirements.txt`) for reproducibility — install exactly
what's pinned rather than the latest version, or you'll hit import errors
for `langchain.retrievers`.
